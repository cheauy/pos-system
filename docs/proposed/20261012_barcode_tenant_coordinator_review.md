# Tenant coordinator review - activation blocked

The v2 proposal is not suitable for activation: its global catalog mutex and global order-allocation mutex queue unrelated businesses. The existing import RPC also takes SHARE ROW EXCLUSIVE table locks. Those table locks conflict with ordinary writers regardless of business, so changing only the advisory mutex cannot meet the requirement that business A's import permits business B's sale.

The approved continuation now adds `20261012_barcode_preservation_v3.PROPOSED.sql`, a reviewable standalone successor composed from the preserved v2 source plus tenant entry, writer adapters and ownership guards. `20261012_barcode_tenant_coordinator_v3.PROPOSED.sql` remains the earlier deliberately noninstallable prototype, not the successor. The runtime still uses the unchanged default-off v2 probe. The successor ends with BOTH v2/v3 readiness probes false; it cannot enable the new flow. No runtime callers, native files, historical migrations, flags or production data were changed during this review. Do not apply or activate any proposal without separately authorized target review.

## Chosen coordination design

Acquire one exact UUID tenant-mutex row before any group/request/table/row/FK locks. Import snapshots cover shared products, branches, stock, customer/supplier/settings records and dependent bookkeeping, so per-identifier reservations alone cannot protect the snapshot. Shared and branch identifier collisions also need one consistent business scope. Tenant entry sacrifices same-business import/sale concurrency intentionally; different businesses do not share a mutex key.

For approved multi-business maintenance, authorize the complete scope first, sort UUIDs and acquire all rows in that order. Nested writers can inherit a subset; widening an existing transaction scope fails. A private xid8/backend record is created only after every lock is acquired. API roles cannot read or forge it, and a request header or GUC is not proof of lock ownership. The earlier persistent prototype covered commit/rollback/savepoint behavior in synthetic tests. The successor uses transaction-cleaned temp proof instead, whose actual execution remains unverified by user choice.

Statement guards reject missing proof before tuples and never acquire a tenant lock late. Row guards verify both old/new tenant ownership and reject reassignment. The successor now includes direct REST, recorded entity-only RPC, child-table, view, new-business genesis and private bulk entry adapters. Missing adapter or missing tenant-mutex row rejects explicitly. These adapters do not certify unknown target authorization or unrecorded callers.

## Identifiers, allocator and authorization remain invariant

Carry v2 exact identifier preservation, alias reservation/collision rules, branch-aware authenticated scan RPCs and readiness fingerprints into the final successor. Product barcode remains a string distinct from SKU, variant group ID and UUID. Identical product codes in separate businesses may be valid; shared/branch collisions within a business still fail. No letters or zeros are stripped. Legacy codes and known aliases remain reserved; overwritten printed values require evidence-based migration review.

Order codes remain immutable, globally unique 12-digit strings matching `[1-9][0-9]{11}`; order display numbers, UUIDs and QR URLs remain separate. Retain the native-compatible Code 39 receipt renderer. The successor removes v2's global `tenh-order-code-allocation` advisory lock. The global unique index remains essential and necessarily coordinates a true same-code collision. A check-before-insert is not uniqueness proof: a rare unsaved candidate race must roll back and retry the complete idempotent creation request safely, never rewrite a saved order. Historical display aliases are business scoped and may overlap across businesses; the allocator's global alias precheck is best effort, not a global alias uniqueness guarantee. Tenant/branch-aware readers and ambiguity handling remain essential. Include cross-business and product/order ambiguity in final integration tests if the user later authorizes them.

Private helpers are callable only by reviewed definers. Public entry adapters must preserve authenticated active membership/team-password/effective permission/requested branch/plan checks; service role is trusted only inside its reviewed operation and explicit scope. An API caller's tenant header is not authorization. Order lookup remains alias-aware only with the preservation capability, denies cross-business/branch or archived access, and opens a unique authorized match rather than choosing arbitrarily.
