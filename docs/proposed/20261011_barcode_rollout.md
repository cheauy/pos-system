The complete new flow is default-off. With no enabled private flag, the legacy path does not probe the new schema and keeps established POS/writer/import/Code 39 label behavior. When TENH_BARCODE_PRESERVATION equals 1, tenh_barcode_contract_v2_ready() must return true. Failure, missing schema or an invalid alias response is UNAVAILABLE, never a legacy downgrade: affected scans, label rendering and identifier writes are disabled. Ordinary POS catalog access, manual selection and checkout stay available; the POS scan callback explicitly rejects scans. Enabled exact lookup never falls back to current fields when an alias RPC fails, preventing an old product alias from appearing to be an order-only match. Group edits still need the existing batch-edit RPC independently. Only the server-resolved label capability is passed to clients; no private flag is bundled there.

In the enabled web flow, missing new codes are generated as 15-digit numeric strings from 48 random UUID bits. Explicit new/replaced product codes must be exact numeric strings of 6-20 digits. Edit/import validation compares saved identifiers: unchanged legacy alphanumeric text remains valid and is never rewritten. Missing import update fields preserve saved codes; missing inserts use the database allocator. JSON numbers are rejected. Zeros stay significant. Codes are internal identifiers, not EAN/UPC/GTIN numbers. Each size/colour product row has its own identity. NULL, empty, padded and unsupported legacy columns stay unchanged. Not every printed legacy barcode is numeric.

Enabled product labels use exact Code 128, its checksum, ten-module white quiet zones, 8 mm height and two dots per module at 203 dpi. A generated code needs about 38.5 mm printable width; 50x30 fits horizontally and 40 mm labels do not. Oversize/overflow blocking applies only to this enabled flow. Default-off labels retain Code 39 fixed-label sizing with exact payloads and white quiet zones. This compatibility path is not physical-print certification.

Web receipts always use native-compatible Code 39, never Code 128. Exact numeric 12-digit order codes use ratio 2:1, two dots per narrow bar at 203 dpi, ten-narrow-module quiet zones and 8 mm height. Their 50.3 mm width fits the 52 mm printable area on 58 mm paper. The immutable globally unique order_code is distinct from display number, UUID and QR URL. Missing/invalid receipt codes require reloading the saved receipt before printing; a saved sale is never retried.

Independent exact-current-field scan lookup remains available while the capability is off. It checks current product barcode/SKU and order-code/display-number matches with business/branch authorization. One authorized order opens its details with scanned=1; multiple matches warn. No zero stripping, prefix scan match or automatic completion occurs. Enabled lookup also reads reviewed aliases. Privileged order contents are never read before authorization. A decoder's alternate UPC/EAN representation requires a proven collision-checked alias.

Random generation is not uniqueness. The SQL proposal serializes claims and reserves case-insensitive identities per business/branch; shared identities cover the business's branches. Backfill reserves known current shared/branch identifiers and order codes/display numbers without changing columns. Conflicts abort the transaction. Old aliases remain reserved after explicit changes; cross-product reuse needs owner review. Overwritten/normalized printed codes cannot be reconstructed automatically. Permanent product/order deletion cascades registry rows; indefinite tombstones and alias-history backup/restore need separate lifecycle review. Soft archives retain aliases while lookup excludes archived records.

Review other target writer entry points, stock/seed paths and deletion/FK interactions before release.

This global coordinator is a conservative draft mechanism, NOT a production-ready multi-tenant design. It was chosen because statement guards can acquire one known lock before tuples without inferring business identity from arbitrary bulk/admin statements, including service inserts without a tenant header. Exact scope: every batch edit; every import RPC kind, including customer/supplier imports; applicable mobile product/bundle operations; product INSERT/DELETE or UPDATE mentioning SKU/barcode; branch-view UPDATE mentioning identifiers; branch-detail and stock INSERT/DELETE; and order INSERT/DELETE or UPDATE mentioning display number/code. Thus ordinary new POS/online order creation can queue behind another business's long import. Stock-quantity-only updates and unrelated mobile operations do not intentionally enter this coordinator. Fixture success proves neither acceptable latency nor scalability; activation remains blocked pending concurrency design review and real-session/load evidence.

Safe alternatives need separate design review: acquire a validated tenant-scoped coordinator at every writer entry before group/table/row locks, require explicit tenant context for raw/admin statements and lock multi-tenant batches in deterministic order; or design per-identifier reservations with database-enforced shared/branch collision rules and consistent lock acquisition. Both require an inventory of all writers, FK/stock/deletion interactions, privilege changes where necessary and real concurrent tests. Do not replace the global coordinator with a row-trigger tenant lock alone: that can reacquire locks after tuples. No such broad redesign or production load testing was performed in this task.
